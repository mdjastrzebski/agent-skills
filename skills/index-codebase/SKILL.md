# Index Codebase

Study the whole repository and write durable docs that let a future agent, starting cold, answer "how does this work?", "where do I change X?", "can I configure or extend Y?", and "how do I get a change in?" without re-exploring the codebase. Use any agent docs the repo already has, but check them against the code and fix or complete them.

Record what is expensive to rediscover: architecture, how parts interact, invariants, why the design is the way it is, and where to look. Skip what is cheap to rediscover: directory listings, file-by-file tours, API signatures, anything already said well in the README.

Project-level questions, such as maintenance activity, backing, license, alternatives, and what contributions are welcome, belong to the `index-github` skill.

## 1. Preflight

```bash
git rev-parse --short HEAD && git status --short | head
bash <skill-dir>/scripts/agent_docs.sh list
grep -rl 'index-codebase:' docs/agents 2>/dev/null
```

The script sits next to this `SKILL.md` and lists the **existing agent docs**: nested `AGENTS.md` / `CLAUDE.md` files, editor rule files, and `docs/agents/` even when it's hidden from git.

- Files carrying the `<!-- index-codebase: ... -->` marker were generated by this skill, and you may restructure, merge, or delete them.
- Every other agent doc is **hand-written**. You may edit it in place to fix errors and fill gaps (step 6). Never delete, rename, or rewrite it wholesale, and don't add the marker to it.
- If `docs/agents/index.md` has the marker, go to **Refresh**.
- If `docs/agents/index.md` exists without the marker, adopt it as the index: audit and extend it rather than writing a parallel one.

## 2. Survey

Get the shape of the repo before reading code in depth: file counts per top-level directory, and change hotspots from the last ~1000 commits.

Read the existing agent docs first, as leads rather than facts, and note every checkable claim (commands, paths, symbols, statements about structure or behavior) for step 6. Beyond the usual README, contributing, manifest, and CI files, look for the sources that answer later steps: decision records (`docs/adr`, `rfcs/`, CHANGELOG breaking changes), release config, lifecycle scripts that run on users' machines, and FAQ, troubleshooting, and limitations pages. Note which files are generated, because hand-editing them is a trap worth documenting.

## 3. Choose the areas

Split the system into 3–10 **areas**: parts that each carry a meaning in the design. Use the system's own names, and reuse an area split from the existing docs if it holds up. In a monorepo, group tiny packages together and split a package that holds two unrelated jobs.

Test the split: knowing only the area list, could someone predict roughly where new behavior would live? If not, re-split.

For a small repo (one package, under ~50 source files), skip areas and put the area content in `index.md`. Fold `using.md` and `contributing.md` into it as well while it stays within its line budget.

## 4. Deep-dive each area

Trace at least one real flow end to end through named files and symbols, and find the invariants, extension points, and tests (and how to run only those). Stop once you can explain the area's core concepts and fill in its "Where to change things" table. You don't need to understand every file.

**If you can run subagents**, give each one a single area to work on in parallel. Pass it the area's name and paths, the existing docs' claims about that area, the path to [references/area-template.md](references/area-template.md), and the writing rules in step 7. Ask for the drafted file, a verdict on each claim, and open questions. Then read every draft yourself, make names and cross-links consistent, and spot-check claims against the code.

## 5. Cross-cutting pass

- **Primary flows:** the 1–3 flows that matter most, traced across areas.
- **Design decisions:** the choices that shaped the system, each with its reason, from decision records, commit messages, and "because" / "workaround" / "HACK" comments. Fetch linked issues only when a decision hinges on them.
- **Conventions:** error handling, logging, config loading, naming, codegen, test style, and which files must not be hand-edited.
- **Glossary:** domain terms that a newcomer would misread.

### Using it

- **What it is and who it's for**, in one paragraph.
- **Platforms and integrations:** supported runtimes and versions, and where each integration's adapter lives.
- **Configuration and extension points:** every config surface with where it's parsed and its defaults; plugin, hook, and registry APIs; how to override one piece without vendoring the whole thing, and what really needs a fork.
- **Known limitations and gotchas:** non-goals, unsupported cases, and failure modes visible in code.
- **Security and trust:** what it executes, network calls and telemetry (hosts, data, opt-out), files written outside the project, required permissions and secrets, and how to report a vulnerability. **For a repo of agent skills, prompts, or rules**, list what each one tells an agent to run, write, delete, fetch, or send, and flag anything destructive or outward-facing.

### Contributing to it

- **Dev setup and feedback loop:** setup, running a single test, lint, typecheck, and end-to-end validation. **For a repo of agent skills or prompts**, explain how to check that a skill triggers and behaves correctly, and say plainly if there's no such check.
- **Contribution rules:** which conventions tooling enforces versus which are only written down; commit and PR format; changesets; CLA or DCO; written review expectations. How review actually goes belongs in `index-github`.
- **Release process:** trigger, versioning, changelog, and how a merged change reaches users.

## 6. Audit existing agent docs

Skip this step if preflight found no hand-written agent docs.

**Correctness.** Label every checkable claim:

- **correct:** leave it as it is.
- **stale:** it was true once, such as a renamed path, a changed command, or a moved responsibility. Update it.
- **wrong:** it contradicts the code. Fix it.
- **unverifiable:** you can't confirm it from the code or history. Leave it, and list it in the report.

Statements like "prefer X", "don't touch Y", or "ask before Z" are the maintainers' policy, not claims about the code, so keep them. Only flag a rule when the repo itself contradicts it, for example a doc that says `yarn` while the lockfile is `pnpm-lock.yaml`.

**Completeness.** Look for missing areas, commands, traps, generated-file warnings, and anything that would send an agent to the wrong place.

**Fix:**

- Make the smallest edit that fixes each problem, keeping the author's structure, voice, and level of detail.
- Put a missing fact in the hand-written doc only if it fits that doc's scope. Put architecture content in the generated docs and link to it.
- When a hand-written doc already covers a topic well, link to it from `index.md` rather than restating it.
- Never let the generated docs contradict a hand-written one. Fix one or the other.

## 7. Write the docs

```text
docs/agents/
  index.md            # always: overview, map, and router; read first
  decisions.md        # cross-cutting design decisions (fold into index.md when there are only a few)
  using.md            # platforms, configuration and extension, limitations, security and trust
  contributing.md     # dev setup and feedback loop, contribution rules, release process
  areas/<area>.md     # one per area
```

If a target file already exists without the marker, it's hand-written. If its scope matches, merge your content into it under the step 6 rules. Otherwise, pick another name and link to that one. (`index.md` is adopted in preflight.)

Start every generated file with the marker:

```markdown
<!-- index-codebase: generated from <short-sha> on <YYYY-MM-DD>. Code wins when it disagrees with this doc. -->
```

Fill the files from the templates in [references/doc-templates.md](references/doc-templates.md) and [references/area-template.md](references/area-template.md). Drop any section that would be empty or padding.

### Writing rules

- Use headings that match likely questions, and tables for lookups.
- Cite file paths and symbol names, never line numbers.
- Give the reason behind each decision. Cite the evidence (a path, commit, ADR, or issue), or prefix a guess with **Inferred:**.
- Link to the README and API reference rather than copying them.
- Keep `index.md` to ~200 lines and every other file to ~300 lines. If an area file grows past that, split the area.

## 8. Verify

Run these checks on both the generated docs and every hand-written doc you edited.

- Every cited path exists: `bash <skill-dir>/scripts/agent_docs.sh check-paths`. Treat each hit as a lead: hand-written docs often use paths relative to a nested `AGENTS.md`, or illustrative paths. Fix only the ones that really point nowhere.
- Every cited symbol exists: check a sample, and all of the `index.md` entries.
- Run the build and test commands when that's cheap. Otherwise mark them "from CI, not run".
- Re-read `index.md` as a newcomer. Can it route each "Where to look" row to the right file?

## 9. Wire it up

Both `index-codebase` and `index-github` link their docs from one shared `## Agent docs` section in `AGENTS.md`. Each skill owns exactly one line in it. Yours links to `docs/agents/index.md`:

```markdown
## Agent docs

- [docs/agents/index.md](docs/agents/index.md): read before exploring the code. Architecture, area map, where to look, usage and extension, contributing. Generated from an earlier commit; verify details against the code.
```

- **Find the section.** Create `AGENTS.md` or append the section if missing. If `AGENTS.md` already lists links to other docs, add your line to that list instead.
- **Edit only your line.** Find it by its link target, `docs/agents/index.md`, since the wording varies between skill versions. Update or add it, once. Leave everything else untouched, and never add `index-github`'s line: its file may not exist yet.
- **Connect `CLAUDE.md`.** If it exists and neither imports nor mentions `AGENTS.md`, add your line to it under `## Agent docs`. If it doesn't exist, create it containing just `@AGENTS.md`.

Don't commit. Report:

- the files written and the areas
- any of the topics from step 5 you couldn't establish, such as "no evals found" or "telemetry unclear"
- every edit to a hand-written doc, each with its label (stale / wrong / missing) and its evidence
- the unverifiable claims, unresolved questions, and **Inferred:** claims worth checking
- a reminder to either commit the changes or add `docs/agents/` to `.git/info/exclude` if they shouldn't go upstream

## Refresh

When the generated docs already exist, diff and log from the sha in the index marker to `HEAD`, then:

- Map changed paths to areas using the Map table. Re-research only the affected areas, and add, merge, or remove areas if the structure itself changed.
- Re-audit (step 6) every hand-written agent doc that changed since that sha, or that cites a changed path.
- Edit sections in place rather than regenerating. Keep hand-added notes inside generated files unless they're now wrong.
- Update the marker sha and date on every generated file you touch, then run **Verify** again.
- Finish with step 9: make sure your `## Agent docs` line is present, then report as usual, listing the areas you refreshed instead of every file.
